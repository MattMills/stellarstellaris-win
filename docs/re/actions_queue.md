# Stellaris 4.5.2 (Linux): fleet action QUEUE and REPEAT mechanics

Source: /opt/stellaris-headless/re/full.asm (objdump of the game binary). All addresses are virtual addresses in that binary.
Token ids come from GetTokenArray() (0x19a5770). The full id->string table is in /root/drawprof/re/tokens.tsv
(generated by /root/drawprof/re/tok.py).

## 0. Data layout (needed for the pseudocode)

CFleet (offsets from the fleet object):

| off | type | meaning |
|---|---|---|
| 0x1208 | CPdxArray<CFleetAction*> | **action queue** (`actions` in the save). Elements at +0x1210 (ptr), count at +0x121c |
| 0x1220 | CPdxArray<CFleetAction*> | **pending-delete list** (not saved). Elements at +0x1228, count at +0x1234 |
| 0x1258 | TFleetFlags | `properties={...}` in the save. Bit word at +0x1260 |

TFleetFlags bits at +0x1260 (from TFleetFlags::WriteMembers 0x2959710, bit i -> token):
0x1 has_custom_name, 0x2 civilian, 0x4 station, 0x8 event_locked, 0x10 weapon, **0x20 mia**, **0x40 action_initialized**,
0x80 friends_should_follow, 0x100 rally_troops, 0x200 mobile, 0x400 valid_for_combat, 0x800 orbital_station,
0x1000 force_evasive_pathfinding, 0x2000 is_cloaked, 0x4000 cloaking_cooldown, 0x8000 can_take_orders,
0x10000 can_construct_megastructures, 0x20000 dirty_cloaking_strength, 0x40000 can_orbitable_repair_ships,
0x80000 stockpile_message_armed, 0x100000 has_scripted_actions, **0x200000 killed**.

CFleetAction (base of every runtime action):

| off | meaning |
|---|---|
| +0x00 | vtable. slot +0x08 deleting dtor, +0x18 WriteMembers, +0x28 ReadMember, **+0x40 Init(CFleet*)**, **+0x48 Update(CFleet*)** |
| +0x08 | bool `done` (token 0x3103 `done`, written only when true) |
| +0x0c | int type token (e.g. 0x1a3 `repeat`, 0x30ff `wait`), used as the save key |

The base CFleetAction::Init (0x2973ba0) is an empty `ret`. Types without their own Init (wait, effect) use it.

CFleetActionData (script-side template): vtable slot **+0x30 CreateInstance(CEventScope&)**, +0x18 Write, +0x28 WriteMembers.

CRepeatFleetAction (size 0x1a0, type token 0x1a3 `repeat`; vtable 0x526d598):

| off | meaning | save key |
|---|---|---|
| +0x10 | const CRepeatFleetActionData* data | `data` (0xf0) |
| +0x18 | int iterations (ctor 0) | `iterations` (0x3101) |
| +0x1c | int index (ctor -1) | `index` (0x20c) |
| +0x20 | CFleetAction* current (null when none) | `current` (0x2ef3) |
| +0x28 | CEventScope scope (contains a CCrudeRandom at scope+0x68) | `scope` (0x2c8d) |
| +0x198 | bool owns_data (set when `data` was read from a save; the dtor deletes data only then) | - |

CRepeatFleetActionData (ctor 0x29690e0):

| off | meaning | script/save key |
|---|---|---|
| +0x40 | CPdxArray<CFleetActionData*> children (ptr +0x48, count +0x54) | every key that is not one of the two below, in file order (CFleetActionFactory::CreateAndReadData 0x29676f0) |
| +0x58 | int max_iterations, default **-1** | `max_iterations` (0x3100) |
| +0x60 | CTrigger* while (null if absent). A named trigger, saved as its id string (trigger+0x88) | `while` (0x3102) |

## 1. Where actions run: on every micro tick, 10 per day

CGameState::HandleTurnTick (0x1b14510) runs on every tick: `state.tick (+0x8) += 1; sub = tick % 10`.
- sub==0 block: day-type and autosave bookkeeping (CStellarisDate::AddDays on a local copy, etc.).
- **On every tick**: UpdateDatabaseArrays() and then **CGameState::MicroUpdate() (0x1b15b10)**.
- sub==4: ProcessAI().
- sub==0: DailyUpdate() (0x1b173a0), *after* that tick's MicroUpdate. Monthly and Yearly updates come after Daily.

So there are **10 MicroUpdates per game day**, and fleet actions advance on each of them.
This is confirmed by CWaitFleetAction::Update (0x296a080): `remaining -= V10`, where V10 = raw 10000 = 0.1 in the
1e5-scale CFixedPoint. So `wait = 10.5` lasts 105 micro ticks.
The save field `tick=` near the top of the gamestate is this counter (CGameState::WriteMembers writes state+0x8 with token 0x385).
The first tick after loading is `tick+1`. The mini save has tick=2.

Order inside CGameState::MicroUpdate:
1. Snapshot fleets: `FleetArraySafe = copy(state+0x4e8 array)`. UpdateDatabaseArrays (0x1b0b9c0) fills that array by walking
   the fleet database slot array in slot order, i.e. **ascending fleet id**, and skips empty slots.
2. CRandom set to forbidden. Parallel CFleet::MicroUpdateParallel over all fleets. The forbidden flag is then restored.
3. For each fleet in the snapshot with IsValid(): CFleet::MicroCombatSerial. Then the modifier node updates.
4. **For each fleet in snapshot order**: `p = fleet.combatManager.GetUpdatedCombatParticipants(); fleet.MicroUpdateSerial(p)`
   (call at 0x1b1637a). Stale refs resolve to the null object and are skipped because its IsValid() is false.
   CFleet::IsValid() (0x29595c0) always returns true. **Random draws are allowed here.**
5. Then CFleetMovementManager::MicroUpdate (all fleets), ship auras, ship updates, PostShipMicroUpdate, and so on.
   So an order that an action issues this tick (e.g. move_to) is executed by the movement manager in the same MicroUpdate.

## 2. CFleet::MicroUpdateSerial(SCombatParticipants const&) - 0x291f460

```
void CFleet::MicroUpdateSerial(participants):
    if flags & MIA(0x20): return                      // MIA fleets: nothing at all (no deletes, no actions)
    if !(flags & KILLED(0x200000)):
        if ShouldForceEmergencyFTL(): movementManager(+0x508).DoEmergencyFTL()
        else:                         combatManager(+0x790).MicroUpdateSerial(participants)
    // flush deferred deletes
    for i in 0 .. pending.count-1 (count re-read each iteration):
        if pending[i]: delete pending[i]              // virtual deleting dtor (vtable+8)
    pending.count = 0

    if actions.count == 0: return
    a = actions[0]                                    // ONLY the head of the queue runs
    if !(flags & ACTION_INITIALIZED(0x40)):
        a->Init(this)                                 // vtable+0x40
        flags |= 0x40
    a->Update(this)                                   // vtable+0x48, in the same call as Init
    if !a->done: return
    actions.RemoveAll(a)                              // stable compaction
    if actions.Find(a) != -1: goto clear              // cannot happen after RemoveAll
    pending.RemoveAll(a)                              // in case ClearFleetActions moved a there during Update
    delete a
  clear:
    flags &= ~0x40                                    // the next head gets Init on the NEXT micro tick
```
Consequences:
- Only actions[0] is ever touched. Init is called exactly once per head. It is guarded by the `action_initialized` flag,
  which persists in the save. Update is called in the same call right after Init.
- When the head finishes (its Update sets `done`), it is removed and deleted in that tick. The next action gets Init + Update
  on the **next micro tick**. There is no idle tick in between, but never two actions in one tick.
- There are no checks for combat, FTL state, current orders, or `event_locked`. MIA skips everything. `killed` only skips
  combat and emergency FTL. Combat manager and emergency FTL run *before* the action in the same call.

Queue manipulation (only these functions touch +0x1208/+0x1220 and the 0x40 bit):
- CFleet::AddActionToQueue(a) 0x2946ac0: `actions.push_back(a); if actions.count == 1: flags &= ~0x40`.
  It is called by queue_actions = CQueueFleetActionsEffect::ExecuteActual 0x372c950:
  `fleet = scope.AccessFleet(); for each child data d (in order): a = d->CreateInstance(scope /* the effect's current scope */); if a: fleet.AddActionToQueue(a)`.
  CreateInstance is where some draws happen (see 5). Appending to a non-empty queue does NOT reset the init flag.
- CFleet::ClearFleetActions() 0x2946bb0: `pending.append_all(actions); actions.count = 0; flags &= ~0x40;
  if autoMove(+0x1308) != 0: SFleetAutoMoveSettings::Reset()`. It is called by clear_fleet_actions
  (CClearFleetActionsEffect::ExecuteActual 0x372cd00) and by CTerraformFleetOrder::StartOrder 0x29db4e0.
  Nothing is deleted immediately. Deletion happens at the start of the fleet's next MicroUpdateSerial. The exception is a
  cleared action that was the running head and finished this tick: the tail above deletes it at once.
- CFleet::RemoveActionToBeDeleted(a) 0x291f880: `pending.RemoveAll(a)` (stable). Its only caller is
  CFindPlanetFleetAction::Update (0x296bcd1), before it deletes a finished child (a double-free guard).

Edge case: an `effect` running inside the head may call clear_fleet_actions on its own fleet and then queue_actions. The new
action then becomes actions[0] with the init flag clear. The old head sits in pending and is freed next tick, or in the tail if
it finished this tick. The CRepeatFleetAction dtor does not delete its `current` child. This only leaks memory and has no
gameplay effect.

## 3. CRepeatFleetAction

### CreateInstance (CRepeatFleetActionData::CreateInstance 0x29692e0)
```
r = new CRepeatFleetAction           // done=false, type=0x1a3
r.data = this; r.iterations = 0; r.index = -1; r.current = null; r.owns_data = false
r.scope = scope; r.scope.CopyInternalScopes(scope)   // full copy incl. root/from/prev chain AND the CCrudeRandom state
```
No draws. The CEventScope ctor and copy only seed or copy a CCrudeRandom.

### Init (0x2969980)
```
void Init(fleet):
    if data.children.count == 0: return          // index stays -1, so the following Update sets done
    done = false; iterations = 0; index = 0
    current = data.children[0]->CreateInstance(scope)   // the child gets a COPY of the repeat scope
    if current: current->Init(fleet)
```

### Update (0x29699e0)
```
void Update(fleet):
    loop:
      if current == null:
          if index == -1: done = true; return
          current = data.children[index]->CreateInstance(scope)
          if current == null: done = true; return          // a child that fails to instantiate ENDS the whole repeat
          current->Init(fleet)
      current->Update(fleet)                                 // runs in the same call as its Init
      if !current->done: return
      delete current; current = null
      index += 1
      if index < data.children.count: return                // the next child is created on the NEXT tick
      iterations += 1
      if data.max_iterations != -1 and iterations >= data.max_iterations: done = true; return
      if data.while and !data.while->Evaluate(scope): done = true; return   // CTrigger::Evaluate(CEventScope&) 0x21190c0
      index = 0; return                                      // child 0 is created on the NEXT tick
```
The loop only re-enters for the create -> Init -> Update path. There is never more than one child Update per call.

Semantics:
- The children are every key of the repeat block except `max_iterations` and `while`. They are instantiated **lazily, one at
  a time, in file order**. Each one is created via its data's CreateInstance(repeat.scope) at the moment it becomes current,
  and is re-instantiated fresh on every iteration.
- `index` is the index of the current child, or of the child that will be created next tick when `current` is absent.
- `iterations` is the number of fully completed passes.
- How a repeat ends:
  - After each pass, the max check comes first. `max_iterations=-1` means unlimited. `0` behaves like 1, because the check only
    happens after a pass.
  - Then `while` is checked. It works like do-while: never checked before the first pass, and evaluated in the repeat's own scope.
  - The repeat also ends at once if its data has no children, or if a child's CreateInstance returns null.
- Timing: if child k finishes on tick T, then child k+1 (or child 0 of the next pass) is created, Init'ed and Updated on tick T+1.
  At top level, the repeat's own Init (which creates and Inits child 0) and its first Update (which Updates child 0) happen in the same tick.
- Double-instantiation corner case: if child 0's CreateInstance returns null in Init, the same tick's Update (index 0, current
  null) calls CreateInstance again. Any CreateInstance draws then happen twice, and if it is null again the repeat is done.

General nesting: every container action (repeat, and find_planet/find_system/find_fleet with `found_*` blocks) holds one
`current` child. It Inits the child when it creates it and forwards Update to it. A child's `done` only means "advance my own
index" to its parent.

Scopes: a repeat passes its own scope by reference to CreateInstance, and CreateInstance copies it, including the CCrudeRandom
state. So every child that a repeat creates starts with the **same crude-random state as the repeat's scope**. In the save, the
repeat has `scope.random={0 1433655165}` and its current find_planet's scope has the identical value. find_planet instead
builds a fresh scope for its found_planet children (see 5).

## 4. Save format (write/read): enough to resume exactly

Fleet (CFleet::WriteMembers 0x291bc70 / CFleet::ReadMember 0x291c620):
```
actions={                       # token 0x30fd, written only if actions.count > 0
    <type>={ ...WriteMembers... }   # one per queued action, in queue order; key = action+0xc token
}
properties={ ... action_initialized=yes ... }   # bit 0x40, so Init is NOT re-run after loading
```
Read: each entry goes through `CFleetActionFactory::CreateAndReadInstance(reader)` (0x2967200) and is appended to the queue.
The pending-delete list is not saved.

CRepeatFleetAction::WriteMembers (0x2969d50) writes, in this order:
```
data={ [while="<named trigger id>"] max_iterations=<int> <child>={...} <child>={...} ... }
index=<int>
scope={ type=... id=... random={ a b } random_allowed=... root={...} from={...} prev={...} ... }
iterations=<int>
[current={ <type>={ ...child members... } }]     # only if current != null
[done=yes]                                       # only if done
```
CRepeatFleetAction::ReadMember (0x2969ab0) reads each key as follows:
- `data`: a new CRepeatFleetActionData, read via CFleetActionData::Read. Children go through CFleetActionFactory::CreateAndReadData,
  and `while` is resolved with CTriggerDatabase::FindNamedTriggerInstance. Sets owns_data = true.
- `index`, `iterations`: ints.
- `scope`: a CEventScope, including the CCrudeRandom state.
- `current`: CreateAndReadInstance of the single inner entry.
- `done`: a bool. The base CFleetAction::ReadMember (0x29682a0) handles `done` for every type.
- Unknown keys go to CPersistent::ReadMember.

Resuming: restore the queue order, the action_initialized bit, and for each repeat its {data, index, iterations, scope, current, done}.
The next MicroUpdateSerial then just calls Update on actions[0], with no Init if the bit is set.
Example (fleet 118 in 2210.02.01-mini): a repeat with 3 find_planet children, max_iterations=-1, iterations=25, index=2,
current=find_planet(graveyard.patrol.3), whose own current is move_to; action_initialized=yes.

## 5. CRandom draws on these paths

The queue/repeat machinery itself makes **zero draws**. I checked CFleet::MicroUpdateSerial, AddActionToQueue, ClearFleetActions,
RemoveActionToBeDeleted, CQueueFleetActionsEffect::ExecuteActual, CClearFleetActionsEffect::ExecuteActual,
CRepeatFleetAction::Init/Update, CRepeatFleetActionData::CreateInstance, and the CEventScope ctor/copy. The CEventScope functions
only construct or copy a CCrudeRandom, which is a local generator. The CRandomLog calls in AddActionToQueue and ClearFleetActions
are logging only. The `while` trigger can only draw if its script does.

All draws reachable from the queue are made by the CHILD types, at the moment the repeat or queue instantiates them or calls their
Init/Update. The scan covered every function whose name contains "FleetAction". In the table, the second argument is the script
line passed to GetIntegerForMacro / GetFixedPointForMacro. The first argument is the source-file string at 0x46b28ac.

| site | function | call | when |
|---|---|---|---|
| 0x2969e30 | CWaitFleetActionData::CreateInstance | GetFixedPointForMacro(line 0x2ba) | **always, 1 per wait instantiation**, even when random=0. remaining = duration(+0x40) + draw*random(+0x48), using a 1e5-scale fixed-point multiply |
| 0x2968aac | COrbitPlanetFleetActionData::CreateInstance | GetIntegerForMacro | conditional: in the branch where the target is a country with owned planets (CalcOwnedPlanets > 0). Probably picks one of them; the orbit_planet RE owns the details |
| 0x2968b62 | COrbitPlanetFleetActionData::CreateInstance | GetIntegerForMacro | conditional: in the galactic-object/deposit branch when the system has planets (count at +0x4a4 != 0) |
| 0x296b75c, 0x296b787 | CFindPlanetFleetAction::Init | GetIntegerForMacro | see the find_planet notes |
| 0x296bddb | CFindPlanetFleetAction::Update | GetIntegerForMacro(line 0x483) | once per found_planet child created while the found planet is valid. It seeds the CCrudeRandom of the new child scope (a new CEventScope set to the planet, with the from/prev chain taken from the action) |
| 0x296cc06, 0x296ce69 | CFindSystemFleetAction::Init | GetIntegerForMacro | |
| 0x296e8ee, 0x296ebba, 0x296ecaa, 0x296efa3 | CFindFleetFleetAction::Init | GetIntegerForMacro | |
| 0x296f646 | CFindFleetFleetAction::Update | GetIntegerForMacro | |

No direct draws in: move_to, wait Update, repeat, or the effect action wrapper. CExecuteEffectFleetAction::Update (0x296a580)
executes its effect in the action's scope and sets done the same tick. Any draws there come from the effect script.

Draw order per micro tick:
1. Fleets run in ascending id order.
2. Within a fleet, combat and emergency-FTL draws (if any) come first. Then the head action's Init (first tick only), then its Update.
3. A repeat runs at most one child CreateInstance (+Init) + Update per tick. So per fleet per tick, the draw sequence for the one
   active leaf chain is: [child CreateInstance draws] [child Init draws] [child Update draws].
